# Decisions

Choices made where SPEC.md was ambiguous or had to be adapted. Newest last.

## Milestone 1 – Skeleton

- **Spring Boot 3.5.16, Gradle 9.9.2.** "Spring Boot 3 (latest stable)" read as the newest 3.x release on Maven Central at build time (2026-11-24); Gradle is the current release.
- **Java 21 bytecode via `options.release = 21`, no toolchain.** A Gradle toolchain would require a local JDK 21 or an auto-provisioning plugin (an unlisted dependency). Compiling with `--release 21` on any JDK 21+ produces Java 21 bytecode and API checks; CI and the Docker build both use JDK 21.
- **No frontend stage in the Dockerfile yet.** `frontend/` does not exist until milestone 6, and `npm ci` fails without a `package.json`. The node stage from the spec is added with the frontend.
- **`bootJar` named `llm-cost-tracker.jar`, plain `jar` disabled,** so the Dockerfile copies one known file instead of a glob.
- **Readiness includes the database.** `/actuator/health/readiness` reports DOWN when Postgres is unreachable; liveness does not depend on it. Health details are hidden (`show-details: never`), since the endpoint is public.
- **Admin password validated at startup** with Bean Validation on `TrackerProperties` (empty or < 12 characters → startup fails). Added in milestone 1 because the compose file already requires the variable.
- **CI runs the compose stack.** Besides `./gradlew test`, the CI `docker` job builds the image, runs `docker compose up`, waits for the container healthcheck and counts the seven tables — the milestone 1 acceptance check, automated.
- **Healthcheck uses `wget`.** Checked on 2026-11-24: `eclipse-temurin:21-jre` (Ubuntu 26.04) ships `/usr/bin/wget` (but not `curl`), so the spec's healthcheck works without extra packages.
- **JVM default time zone pinned to UTC** in `main()` and in the test JVM. The spec stores all timestamps in UTC; also, pgjdbc sends the JVM zone on connect and Postgres 16 rejects legacy aliases such as `Asia/Calcutta`, which broke startup on such hosts. Budget periods will use `TRACKER_TIMEZONE` explicitly.
- **Compose image is `llm-cost-tracker:latest` for now.** The spec's `ghcr.io/OWNER/...` placeholder is rejected by Docker (repository names must be lowercase). Milestone 9 switches it to the real GHCR path once the owner and project name are settled.
- **Dependabot ignores major bumps of Spring Boot and `eclipse-temurin`.** The spec pins Spring Boot 3 and Java 21; Dependabot opened 3.5→4.2 and 21→25 PRs on the first run. Minor and patch updates still flow.
- **`.env` also passed to the app via `env_file` (optional)** so any `TRACKER_*` variable added to `.env` reaches the app without editing the compose file.

## Milestone 2 – OpenAI non-streaming proxy

- **OpenAI usage fields verified on 2026-11-24** against the API reference (developers.openai.com, Chat object). `prompt_tokens`, `completion_tokens`, `prompt_tokens_details.cached_tokens` and `completion_tokens_details.reasoning_tokens` match the spec. The reference also lists `prompt_tokens_details.cache_write_tokens`, which the spec says OpenAI does not have; it is **not recorded** in v0.1 (the docs do not say whether it is billed separately or included in `prompt_tokens`). Revisit when OpenAI documents its billing.
- **Fixtures are real-shaped, not captured.** `fixtures/openai/*.json` follow the documented `ChatCompletion` schema with made-up IDs and counts. They are pretty-printed on purpose, so the byte-identity test would catch any re-serialisation.
- **The SDK test also sets `X-Tracker-Key`.** With `TRACKER_REQUIRE_PROJECT_KEY=true` (the default) the project key header is needed. SDKs set it as a default header in client config (`putHeader`, `default_headers`), so the calls themselves are unchanged.
- **Without a key and with `TRACKER_REQUIRE_PROJECT_KEY=false`, calls are forwarded but not recorded,** because every `usage_event` needs a project. The simplest option; revisit if users want a default project.
- **`Accept-Encoding` is removed only on recorded calls,** so the upstream answers uncompressed and the side copy can be parsed. The client still receives exactly the bytes the upstream sent. Other paths keep the client's `Accept-Encoding`.
- **Streaming requests (`"stream": true`) and `text/event-stream` responses are relayed but not recorded** until milestone 5.
- **Project keys are cached in memory,** refreshed every 30 s and on each cache-miss lookup, so known keys keep working while Postgres is down. An uncached key that cannot be checked because the database is down gets **503 `tracker_unavailable`**, not 401. Keys are looked up by their SHA-256 hash; comparing digests this way leaks nothing useful through timing, so no separate constant-time compare is added.
- **Upstream connection failures return 502 `upstream_unavailable` (504 `upstream_timeout` on timeout) and are not recorded**, since no upstream status or usage exists.
- **Recording parses after the last byte is sent** (`doFinally` on the relay), so it never delays the response. Latency is measured to that point. A client disconnect marks the event `incomplete`.
- **The batch writer loads the whole `model_price` table once per batch.** The table is small, and this keeps prices current with no cache to invalidate.
- **Hikari `connection-timeout` lowered to 5 s** so the writer notices an outage fast and drops (and counts) the batch rather than blocking for the 30 s default.
- **Project key CLI is `--create-project=<name>`.** When that flag is present the app starts without a web server, prints the key once to stdout, and exits (code 0; 1 for a duplicate name; 2 for a bad name).
- **Redacting log converter** replaces Logback's `%m`/`%msg`/`%message` (`logback-spring.xml`). It masks `Authorization`, `x-api-key` and `X-Tracker-*` values, bearer tokens, and `sk-…`/`trk_…` keys. The proxy never logs these on purpose; the converter is the safety net the spec asks for.
- **Test-only dependencies added: `com.openai:openai-java` 4.112.0 and OkHttp `mockwebserver` 4.12.0** (pinned: Spring Boot 3.5 no longer manages OkHttp; 4.12.0 is the OkHttp version the SDK uses). Both are named in the spec's Testing section. A small `Await` helper is used instead of adding Awaitility.
- **Custom OpenAI-compatible providers (`TRACKER_CUSTOM_PROVIDERS`) wait for milestone 3**, as the spec's milestone list says.

## Milestone 3 – Anthropic, Responses API, custom providers

- **Anthropic usage fields verified on 2026-11-26** against the Messages API reference and the prompt-caching guide (platform.claude.com). `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens` match the spec. The docs define total input as `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, so `input_tokens` excludes cached tokens and is **stored as reported**. If `cache_creation_input_tokens` is missing, the per-duration breakdown `cache_creation.ephemeral_5m_input_tokens + ephemeral_1h_input_tokens` is used.
- **One cache-write price per model in v0.1.** Anthropic's docs price cache writes by duration: 5-minute entries at 1.25× the base input price, 1-hour entries at 2×. `model_price` has one `cache_write_per_mtok` column, and the seed file (milestone 8) will fill it with the **5-minute** price, Anthropic's default. 1-hour writes are therefore under-costed. Listed in the README under known limitations. A later migration can add a 1-hour column priced from `cache_creation.ephemeral_1h_input_tokens`.
- **Anthropic `output_tokens_details.thinking_tokens` is stored in `reasoning_tokens`** for display only. The spec's table says Anthropic has no reasoning field, but the current docs report one. Thinking is billed as output and is already inside `output_tokens`, so cost is unchanged.
- **Responses API usage fields verified on 2026-11-26** (developers.openai.com, Responses object): `usage.input_tokens`, `usage.output_tokens`, `usage.input_tokens_details.cached_tokens`, `usage.output_tokens_details.reasoning_tokens`. The reference page does not say whether `input_tokens` includes cached tokens. The spec says it does (as for Chat Completions), so the cached part is subtracted. The reference also lists `input_tokens_details.cache_write_tokens` (with 30-minute and 12-hour breakdowns). Like Chat Completions' field (milestone 2), it is **not recorded** in v0.1, because the docs do not say how it is billed.
- **Only `POST` to the exact endpoint path is recorded.** `GET /responses/{id}` is forwarded but not recorded, since it would double-count the original call. So are `/v1/messages/count_tokens` and `/v1/messages/batches` (batch APIs are out of scope).
- **Custom providers parse as OpenAI and are priced under their own name.** `usage_event.provider` is the configured name (e.g. `groq`), so a custom provider needs its own `model_price` rows. It never borrows OpenAI's prices, because the same model name can cost differently on another host.
- **`TRACKER_CUSTOM_PROVIDERS` is validated at startup.** Names must be lowercase slugs (`[a-z0-9][a-z0-9-]{0,31}`) and may not reuse `openai`/`anthropic`. URLs must be absolute `http(s)` with a host and no credentials, query or fragment. Any mistake stops startup rather than silently routing traffic elsewhere.
- **Integration tests share one Spring context** (`ProxyIntegrationTestBase`, with three MockWebServers for OpenAI, Anthropic and a custom provider), so the slower context start-up happens once.
- **Test-only dependency added: `com.anthropic:anthropic-java` 3.14.0** (uses OkHttp 4.12.0, the same as `openai-java`).
- **OkHttp / MockWebServer major bumps are ignored by Dependabot** (`com.squareup.okhttp3:*`, semver-major). MockWebServer 5 pulls in OkHttp 5, while both provider SDKs used in tests (`openai-java` 4.112.0, `anthropic-java` 3.14.0) are built on OkHttp 4.12; mixing them puts two incompatible OkHttp lines on the test classpath. PR #7 (4.12.0 → 5.5.1) was closed on 2026-11-27 for this reason. Revisit when the SDKs move to OkHttp 5; minor and patch updates still flow.
- **Anthropic credentials pass through in whichever header the client uses.** `anthropic-java` 3.14.0 sends `Authorization: Bearer …` (as the current API reference shows) rather than `x-api-key`. The proxy forwards both untouched and never logs either. Tests cover both forms.
- **Anthropic thinking tokens are already inside `output_tokens` (checked 2026-11-27).** The thinking-cost page says thinking is "billed as output tokens" and "`output_tokens` remains the inclusive, authoritative total used for billing"; `output_tokens_details.thinking_tokens` is a breakdown that is always ≤ `output_tokens`. Cost therefore uses `output_tokens` only, and a regression test uses the docs' example (348 output, of which 312 thinking).

## Milestone 4 – Attribution

- **The request path never touches the database for attribution.** The proxy works out an `AgentRef` (header slug, path slug, fingerprint hash, or `unattributed`), the run ID and tags in memory. The batch writer turns the `AgentRef` into an `agent.id` inside its insert transaction: `agent_alias` first (`slug` or `fp:<hash>`), then the agent. This keeps the milestone 2 guarantee that a database outage never affects a client call. It also matches the spec's "update last_seen in the batch writer, not per request".
- **Concurrency-safe creation through the database, not locks in Java.** Named agents use `INSERT … ON CONFLICT (project_id, name) DO UPDATE … RETURNING id`. Fingerprint agents use `INSERT … ON CONFLICT DO NOTHING`, then re-read the row by name: the same fingerprint means a concurrent creator (use it), a different one means a collision (try a longer name). This holds across several app instances, not just the single writer thread. Tests race 16 transactions at once.
- **Fingerprint names grow 4 → 6 → 8 hex characters on a collision,** as the spec says. They then continue to 12, 16, 24, 32 and 64, so a pathological project can never fail to name an agent. A name held by a merged agent's alias also counts as a collision.
- **The fingerprint is computed only when no header or path agent matched.** The prompt text exists only in local variables inside `Fingerprinter`. A test dumps every table in the schema as JSON and searches it for a marker string from the system prompt.
- **Chat Completions `developer` messages count as system prompt,** joined with `system` messages in request order. Content may be a string or an array of `{"type":"text","text":…}` parts (likewise for Anthropic `system` blocks); non-text parts are ignored.
- **Masking order is UUID → email → ISO date → number,** so a UUID or a date is not broken up into separate numbers first.
- **Merge locks both agent rows (`SELECT … FOR UPDATE`, in id order) and does everything in one transaction.** It re-points the old agent's existing aliases, adds aliases for its name and fingerprint, moves its events, widens first/last seen, and deletes it. A test makes the final `DELETE` fail with a trigger and checks that no alias or event change survived. Budgets on the merged-away agent are deleted with it (`ON DELETE CASCADE`); revisit in milestone 7. Rename and merge are service methods for now; the REST endpoints arrive in milestone 6.
- **Known race:** an event that the writer resolved to agent A just before A is merged away can re-create A, which can simply be merged again. Making the writer and merge fully serialise would put a lock on the hot path for a rare admin action.
- **Run ID:** 1–128 printable ASCII characters after trimming; anything else is ignored (debug log, value not logged). **Tags:** up to 10 per request in header order; the key is slugged and cut to 32; the value is 1–128 printable characters; the first occurrence of a key wins. Empty tags are stored as `NULL`, not `{}`.
- **Path-based project key `/proxy/k/{key}/{provider}/…`.** It is for clients that can only change a base URL; the header stays recommended, and when both are given the header wins. `k` is reserved and cannot be a custom provider name. Redaction:
  - the key segment is stripped before forwarding;
  - `ProxyRoute.toString()` masks it;
  - the optional access log (`TRACKER_ACCESS_LOG`, Reactor Netty) formats an already-redacted URI;
  - the Logback message converter and a new `%wEx` throwable converter mask `/proxy/k/<anything>` in every other log line and stack trace.

  Tests run with the access log and web/Netty DEBUG logging on, and assert that the key is in no log line while the masked access log line is present.
- **No REST/UI for agents yet;** `agent.display_name` is set only through `AgentService.rename` until milestone 6.

## Milestone 5 – Streaming

- **Streaming formats verified on 2026-11-27.**
  - *Chat Completions:* developers.openai.com, chat streaming events and `stream_options`. `include_usage` streams "an additional chunk ... before the `data: [DONE]` message" whose `choices` "will always be an empty array"; all other chunks carry `"usage": null`.
  - *Responses:* the reference page is several million characters long, with the streaming events section out of reach, so the wire names come from the official `openai-java` 4.112.0 SDK's generated event classes. They are `response.completed`, `response.failed` and `response.incomplete` (each with `type`, `sequence_number` and a `response` object carrying `usage`), and `error` (with `type`, `code`, `message`, `param`, `sequence_number`).
  - *Anthropic:* the streaming guide says `message_delta` usage counts "are *cumulative*". So the last value wins, including any input or cache fields a delta repeats.
- **Flushed per chunk.** `text/event-stream` responses are written with `writeAndFlushWith`, one flush per upstream chunk. A test throttles MockWebServer to 300 bytes per 300 ms and checks that the first `data:` line reaches the client in under 1.2 s, while the stream takes more than 2 s.
- **Bounded memory: 64 KiB head + 64 KiB tail per SSE line.** The tracker never holds more than the current line's first and last 64 KiB. Lines are usually tiny. The exception is the Responses `response.completed` event, which repeats the full output: its `type` and `model` are read from the head and `usage` from the tail. Unescaped `"usage":` can only be a real key, because quotes inside JSON strings are escaped. Tests feed a 20 MB `response.completed` line and a 16 MB, 200,000-chunk stream, and assert that memory stays within the window.
- **`stream_options.include_usage` injection is textual.** The field is inserted before the closing brace of the top-level object, so every other byte of the request is unchanged. It applies only to streamed Chat Completions on the OpenAI dialect (OpenAI and custom providers) that do not set `stream_options` at all. If the client set `stream_options`, with or without `include_usage`, the request is untouched and a stream without usage is recorded `incomplete` with zero tokens, as requested. A custom provider that rejects `stream_options` can be handled by turning the injection off globally (`TRACKER_OPENAI_INJECT_STREAM_USAGE=false`); a per-provider switch can come later.
- **What counts as a normal end.**
  - Chat: `[DONE]` *and* a usage chunk.
  - Responses: `response.completed`.
  - Anthropic: `message_stop`.

  Anything else (client disconnect, upstream drop, an error event, `response.failed`/`response.incomplete`, a missing usage chunk) records the event with `incomplete = true` and the usage seen so far. Mid-stream errors keep the HTTP status the stream started with (usually 200), since there is no separate error column.
- **Client disconnect cancels the upstream request.** The client write is cancelled, which cancels the upstream body subscription, and Reactor Netty closes that connection, so the provider stops generating. A test uses a JDK `HttpServer` streaming one chunk every 100 ms for 30 s. It resets the client socket after the third chunk and asserts that the upstream's next writes fail within seconds. A client that disconnects *before* the upstream responds cancels the upstream call too, but nothing is recorded, since there is no status or usage yet.
- **Upstream connection drops mid-stream are passed on, not hidden.** The response is already committed, so the proxy closes the client connection and the client sees a broken stream, exactly as it would talking to the provider directly. The event is recorded as incomplete.
- **A streamed request that gets a non-stream response** (e.g. a 400 JSON error) is recorded through the non-streaming path with `streamed = false`.

## Milestone 6 – Dashboard API

- **Scope: the API only.** Every `/api` endpoint in SPEC.md is built, including the ones whose behaviour belongs to later milestones, so the UI can be built against the whole surface:
  - Budgets have full CRUD, current-period spend and projection now. Alert evaluation, the webhook, the in-memory spend cache and enforcement come in milestone 7. The `enforce` flag is stored but has no effect yet, and `/alerts` lists whatever `alert_event` holds, which is nothing until then.
  - Prices can be listed (with the models seen without a price), added and recomputed now. The seed price file comes in milestone 8.
- **No Spring Security.** It is not in the Tech stack list, and the needs are small (one password, one instance), so sessions, CSRF and the rate limit are about 250 lines in `auth/`, written by hand and covered by `AuthApiTest`.
  - *Sessions:* 32 random bytes from `SecureRandom` in an `HttpOnly`, `SameSite=Strict`, `Path=/` cookie, marked `Secure` when the request came over HTTPS. Only the SHA-256 of the id is kept as the map key. Idle timeout 12 h, absolute 7 days, at most 1,000 sessions (the oldest is dropped). Sessions live in memory, so a restart signs the admin out. A login always issues a fresh id, which prevents session fixation.
  - *CSRF:* a synchronizer token, 32 random bytes per session, returned by login and by `GET /api/auth/session` (the cookie is HttpOnly, so the UI cannot read it). `POST`, `PUT`, `PATCH` and `DELETE` must send it in `X-CSRF-Token`, compared in constant time; otherwise the call gets 403 `csrf_token_invalid`. Login itself has no token: it accepts only `application/json`, which a cross-site form cannot send without a CORS preflight (and no CORS is configured), and the cookie is SameSite=Strict.
  - *Password check:* the SHA-256 digests of the given and configured passwords are compared with `MessageDigest.isEqual`, so the comparison time does not depend on where the strings differ.
  - *Login rate limit:* 5 attempts per minute per client IP, as a sliding window. Every attempt counts, successful or not, and refused attempts are not added. The 6th gets 429 `rate_limited` with `Retry-After`. The client IP is the TCP peer; `X-Forwarded-For` is trusted only when `SERVER_FORWARD_HEADERS_STRATEGY=native` is set, since any client can send it. Memory is bounded: idle entries are purged every minute, and the map is cleared above 100,000 IPs. Entries "in the future" are dropped, so a clock stepping back (NTP) cannot lock an IP out.
- **The admin password, session id and CSRF token never reach the logs, even at DEBUG.** A test with Spring web and Netty loggers at DEBUG first caught Spring's codec logging printing decoded bodies (`Decoded [LoginRequest[password=…]]`) and the encoded login response with its CSRF token. Both records now mask their own `toString()`, and the log redaction safety net also masks `password`, `secret` and CSRF-token values. `AuthApiTest` captures the output and asserts that none of the three appears.
- **`GET /api/auth/session` is an extra endpoint** not in the spec's table. The UI needs it to recover its CSRF token after a page reload.
- **One error shape everywhere under `/api`**: a `WebExceptionHandler` that runs before Boot's default handler turns validation, malformed JSON, unknown fields, bad path or query values, 404 and 405 into `{"error":{"code","message"}}`. Messages name the field and never echo the value sent. Unknown JSON fields are rejected globally (`spring.jackson.deserialization.fail-on-unknown-properties=true`); the proxy is unaffected because it never binds bodies to classes.
- **Money as decimal strings with a fixed scale:** costs have 8 decimal places (the `NUMERIC(14,8)` column), limits 2, prices 6. Shares and rates are fractions with 4 decimal places, e.g. `"0.4170"`, and `null` when the denominator is zero. Unpriced events count as zero cost and are reported separately (`unpricedRequests`, `unpriced`).
- **Time:**
  - `from`/`to` are ISO-8601 instants or dates. A date means midnight in `TRACKER_TIMEZONE`.
  - The default range is the last 14 days up to now, and the longest range is 400 days. `interval=hour` allows at most 31 days.
  - `TRACKER_TIMEZONE` is introduced now, not in milestone 7, because day buckets and budget periods need it. Postgres groups events into 15-minute UTC slots, and Java maps each slot to its hour or day in the zone and fills empty buckets with zeros. It uses `atStartOfDay`, so DST days are right. Every zone in use today is offset from UTC by a multiple of 15 minutes, so a slot never straddles a local boundary.
  - Tests run with Asia/Kolkata, where hours start at :30 UTC.
- **Change vs the previous period** compares cost with the equal-length range just before `from`, as a fraction (`"1.1000"` = +110 %). It is null when the previous period cost nothing.
- **Incomplete calls are their own count** (`incomplete`, `incompleteRate`) beside `errors`/`errorRate` (status ≥ 400). The two are independent: a stream cut off mid-way keeps its 200 status.
- **Average cost per run** = the cost of calls that carry a run id ÷ the number of runs. Calls without a run id don't dilute it.
- **Budget projection:** spend so far ÷ elapsed time × period length, with elapsed time floored at one hour so the first call of a day doesn't project wildly. The projected alert date is when the same rate reaches `alert_pct`, if that is inside the period. Spend is read from `usage_event` on demand, only when the project has budgets. On the summary and agents endpoints it is tagged in the same pass as the range (see Performance); the budgets endpoints use one scan from the start of the month. Milestone 7's in-memory spend can replace it.
- **Runs:** a call's `created_at` is when it finished (milestone 2), so a call started at `created_at − latency_ms`.
  - A run starts with its earliest call start and ends with its latest call end, and `durationMs` is the difference. Waterfall offsets are measured from the run start.
  - The list is ordered by last activity, newest first, with run id as a tie-break, and is limited to the range (default 14 days). The page is found by walking the range's events backwards from the newest, through `ue_project_time`, 1,000 at a time. Only the runs met on the way are aggregated, through `ue_run`. The walk stops once 50 runs are known to end after the walk position, because any run not met yet ends at or before it. A page therefore costs a few thousand index entries, not a `GROUP BY` over every run in the range. A test pages through 3,000 interleaved runs and compares the result with a plain `GROUP BY … ORDER BY`.
  - The cursor is opaque: base64url of the last row's end time and run id. Paging uses a row comparison in `HAVING`, so ties never repeat or skip a run.
  - Run detail returns at most 2,000 calls, with `truncated` set when there are more.
- **Agents with no calls in the range still appear**, with zeros, so a newly renamed or quiet agent doesn't vanish from the Agents screen.
- **Key rotation takes effect at once on this instance.** The new hash replaces the old one in the table, and the proxy's key cache evicts the project's entries. A generation counter stops an in-flight refresh or lookup from putting the old key back. Other instances would stop accepting the old key at their next 30 s refresh, but v0.1 runs one instance.
- **CSV export streams.** It uses a read-only transaction with a server-side cursor (fetch size 1,000) and is emitted 500 rows per chunk through `Flux.generate`. Memory stays flat, and a client that stops reading stops the query.
  - Columns are fixed and include the agent's name and source, not its id.
  - Values are RFC 4180 quoted. A value starting with `= + - @`, tab or CR gets a leading apostrophe, because run ids and tags come from request headers and could otherwise carry spreadsheet formulas.
- **`/api/status` `lastEventAt`** is the newest event by primary key (no extra index needed), or, with `?projectId=`, the newest event of that project via `ue_project_time`. If the database is down, it still reports drops and queue depth.
- **Recompute** walks the primary key in batches of 5,000, one short statement per batch. With `all=false` it prices rows that have no cost; with `all=true` it re-prices every row in the range, and an event with no matching price is set back to null. One recompute runs at a time; a second gets 409.
- **`--seed-demo[=name]` with optional `--seed-demo-events=n`** (default 25,000, at most 5,000,000) writes straight to the database in one transaction, then runs `ANALYZE`.
  - It creates 4 agents: two by path, one by header, and one fingerprint agent that first appears 7 days in.
  - It uses 4 models, runs of 2–11 calls (triage first), standalone calls, about 0.5 % errors (429/500/529/400), about 1 % incomplete streams, and cache reads and writes.
  - Traffic has a weekday and daytime rhythm in `TRACKER_TIMEZONE`, and grows 45 % over the month.
  - It adds a monthly project budget and monthly budgets for the three named agents, sized from the generated spend.
  - Costs come from the price table when it has the model. Otherwise they use placeholder rates in `DemoData.ILLUSTRATIVE_RATES`, which are labelled as not provider prices and never written to `model_price`, so the milestone 8 seed file is not blocked by fake rows.
  - Like `--create-project`, it runs only when its flag is given, with no web server, and exits.
- **Performance (1M events, under 500 ms per call).** No new index was needed: every query is bounded by project and time and uses `ue_project_time` (or `ue_run`). The work went into doing one cheap pass per endpoint:
  - *One pass, several windows.* The summary needs the range, the previous period and, if there are budgets, the current budget day and month. These are boolean group keys in a single scan (`GROUP BY agent_id, in_range, in_previous, in_month, in_day`), not separate scans. The agents endpoint does the same per agent and model.
  - *No `DISTINCT` over the range.* `count(DISTINCT run_id)` and `count(DISTINCT agent_id)` sort every row. Active agents now come from the small grouped result. Runs are counted with `GROUP BY run_id` in a subquery, which is a hash aggregate.
  - *Cheap buckets.* `date_trunc(…, zone)` per row costs a time-zone conversion for every event. `floor(date_part('epoch', created_at) / 900)` is plain arithmetic, and Java maps the few thousand slots to local buckets.
  - *Runs by walking the index* (above).
  - *A plan per query.* PostgreSQL switches a prepared statement to one generic plan after five executions. With ranges from an hour to months, that made 30-day calls jump from 0.43 s to 1.4 s, so the pool sets `plan_cache_mode = force_custom_plan` on each connection. Planning costs well under a millisecond here.
  - *The demo seed runs `VACUUM (ANALYZE)`*, as autovacuum would on a live table, so index-only scans need no heap fetches and autovacuum doesn't start in the middle of a measurement.
  - Measurement: `./gradlew :backend:perfTest` (manual, excluded from `test`), and the manual `perf.yml` workflow on a standard GitHub runner (4 vCPU, stock Postgres 16 in Testcontainers). Both seed 1,000,000 demo events over 30 days (224k runs) and time each endpoint over HTTP: one warm-up, then 5 calls. On the development laptop the timings were unusable, because the machine was heavily throttled: a plain 10M-iteration Python loop took 4–5 s instead of about 0.6 s. The reference numbers therefore come from the runner, [perf run 45991346490](https://github.com/hrushi2311/LLM-Cost-Tracker/actions/runs/45991346490). Slowest of 5 calls:

    | Endpoint | 14 days | 30 days |
    |---|---|---|
    | summary | 289 ms | 360 ms |
    | timeseries (agent/day) | 286 ms | 432 ms |
    | timeseries (model/hour) | 324 ms | – |
    | agents | 259 ms | 274 ms |
